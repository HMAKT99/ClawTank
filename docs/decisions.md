# Architecture Decision Records

Format: context → decision → consequences. Newest last. Status is *Accepted* unless noted.

## ADR-001 — Rust protocol core + Swift native host
**Context.** We need a full RDP server (TLS, NLA, EGFX/H.264, virtual channels) plus deep macOS integration (ScreenCaptureKit, VideoToolbox, CGEvent, private CGVirtualDisplay). IronRDP (Apache-2.0/MIT) has a maintained, feature-rich server crate; macOS APIs are best used from Swift.
**Decision.** Protocol in Rust on `ironrdp-server` (pinned, `egfx` feature). Everything Mac-specific in Swift. Rust is built as a static library linked into the app.
**Consequences.** Two toolchains (cargo + Xcode). The FFI boundary must stay narrow. Our protocol behavior tracks IronRDP releases, so we contribute fixes upstream (e.g. IronRDP #2148).

## ADR-002 — FFI: hand-written C ABI, header generated by cbindgen
**Context.** Options: UniFFI, swift-bridge, hand-written C ABI. The hot path will pass IOSurface-backed frames and encoded H.264 buffers; we want zero-copy and an auditable, fuzzable surface.
**Decision.** `extern "C"` functions with a `ct_` prefix and `#[repr(C)]` types live only in `core/clawtank-core/src/ffi.rs`. `build.rs` runs cbindgen to emit `core/include/clawtank_core.h`, and Swift imports it as module `ClawTankCore` via a module map. Strings returned to Swift are `'static`. Release builds use `panic = "abort"`, so nothing unwinds across the boundary.
**Consequences.** More boilerplate than codegen tools, but no hidden copies or runtime. Every new FFI function needs a Swift wrapper in `CoreBridge` and a fuzz/unit test.

## ADR-003 — Authentication: dedicated app password for NLA
**Context.** NLA (CredSSP/NTLM) requires the server to know the plaintext password or its NT hash. A macOS login password cannot be checked that way without storing a copy. Stock `mstsc` and Windows App must work with default settings (NLA on).
**Decision.** On first run the user sets a ClawTank password. It's stored in the Keychain and passed to `RdpServer::set_credentials` with the macOS short username. Lockout, rate limiting and audit logging go through IronRDP's `CredentialValidator` hook.
**Consequences.** Users type a separate password in their client. A macOS password change doesn't break RDP. NTLM is weak against offline cracking of captured exchanges, which is one more reason to stay LAN-only by default and to enforce a minimum password strength. Kerberos is out of scope.

## ADR-004 — Virtual displays via private `CGVirtualDisplay`, isolated and optional
**Context.** Headless Macs and resolution matching need a virtual display. No public API exists. `CGVirtualDisplay` (CoreGraphics, private) works on macOS 15.6 (see docs/research/virtual-display.md).
**Decision.** Access it only through a `VirtualDisplayProvider` protocol. Feature-detect with `NSClassFromString`, guard every call, and fall back to capturing the physical display. Sweep stale displays at launch. Interface declarations live in a single ObjC header.
**Update (Phase 4, measured on macOS 15.6).** Readiness and resize checks use `CGDisplayBounds`, because `CGDisplayCopyDisplayMode` often returns nil for virtual displays. Retina→1x doesn't apply in place, so `DisplayService` recreates the display; other transitions resize in place. A display released earlier in the same process doesn't affect later ones. No launch-time sweep is needed: displays die with the process.
**Consequences.** Not App-Store-eligible (already a non-goal). It may break in a future macOS, which the fallback limits to a degraded experience rather than an outage. We test on each macOS beta.

## ADR-005 — Minimum macOS 14 Sonoma
**Context.** ScreenCaptureKit's `SCScreenshotManager`, `MenuBarExtra` and `SMAppService` are available on 14. Nothing so far requires 15.
**Decision.** Deployment target 14.0. Raise it only through a new ADR.
**Consequences.** We must test on 14 before releases (CI runs macOS 15 runners only).

## ADR-006 — Xcode project generated by XcodeGen
**Context.** Hand-edited `.pbxproj` files cause merge conflicts and are hard to review.
**Decision.** `app/project.yml` is the source of truth. `make project` generates `ClawTank.xcodeproj`, which is git-ignored.
**Consequences.** Contributors need `brew install xcodegen`. Opening the project in Xcode requires `make project` first.

## ADR-007 — Build for the host architecture; universal later
**Context.** We optimize for Apple silicon. A universal binary doubles Rust build time and needs the `x86_64-apple-darwin` target.
**Decision.** `make build` builds for `$(uname -m)`. Universal (lipo) packaging will be added to `make release` in Phase 10 if Intel support stays cheap.
**Consequences.** Dev builds are fast. Release tooling has to handle lipo.

## ADR-008 — Accept RUSTSEC-2023-0071 (`rsa` Marvin attack) for now
**Context.** `cargo audit` flags `rsa 0.10.0-rc.18`, pulled in by IronRDP's `picky`/`sspi`. No fixed version exists. The attack needs an RSA PKCS#1 v1.5 *decryption* oracle using the server's private key.
**Decision.** Ignore it in `core/.cargo/audit.toml`, after verifying our path: TLS private-key operations go through rustls with aws-lc-rs; NLA uses NTLM (HMAC/RC4, no RSA); Kerberos (whose sspi decrypts are symmetric anyway) is not enabled. We also raised the workspace MSRV to Rust 1.88 to take `time ≥ 0.3.47` (RUSTSEC-2026-0009).
**Consequences.** We re-check this whenever IronRDP is bumped and remove the ignore once `rsa` ships a constant-time release. If we ever enable Kerberos or RSA key transport, this ADR must be revisited.

## ADR-009 — Stay on released `ironrdp-server 0.13.0`; own the accept loop
**Context.** Phase 0 research read IronRDP *master*, which carries unreleased APIs under the same version number (`ConnectionSource`/`serve`, `on_connection_info`, suppress-output context, server-side RDPDR). The published 0.13.0 has `run()` and `run_connection(stream)` only.
**Decision.** Depend on the released crate, not a git revision. `server.rs` runs its own accept loop (bind → LAN check → `run_connection`), which also gives synchronous bind errors and port-0 support. IronRDP only calls `RdpServerDisplay::updates()` after authentication and capability exchange, so we use that call as the "session started" signal. We enable `with_honor_client_desktop_size(true)` and only clamp sizes no valid client sends.
**Consequences.** We re-check for these APIs when IronRDP publishes a new release, and Phase 7 file transfer depends on RDPDR server support shipping. The accept loop is about 40 lines we maintain ourselves.

## ADR-010 — TLS identity: self-signed RSA-2048, generated in Rust, stored in the Keychain
**Context.** Stock clients must accept our certificate, and users verify it by fingerprint. IronRDP's `helper` module loads PEM files and enables `KeyLogFile`.
**Decision.** `rcgen` (aws-lc-rs backend) generates RSA-2048 with roughly a 3-year validity, CN = `<host>.local`, EKU serverAuth. We build our own rustls `ServerConfig` with an explicit aws-lc-rs provider and no key logging. Swift persists the certificate DER and PKCS#8 key DER: Keychain generic-password items (`dev.clawtank.ClawTank`, `AfterFirstUnlockThisDeviceOnly`, so a headless Mac works after reboot and auto-login) for signed builds, and an owner-only file for ad-hoc builds (ADR-013). The fingerprint stays stable across launches.
**Consequences.** Certificate rotation UI comes in Phase 5.

## ADR-011 — LAN-only means a peer-address filter, not interface binding
**Context.** IronRDP binds a single address. Binding each LAN interface separately is fragile (DHCP, Wi-Fi/Ethernet changes).
**Decision.** Bind `0.0.0.0:3389`, and refuse any peer outside loopback, RFC 1918, 169.254/16, 100.64/10 (CGNAT, used by Tailscale), fc00::/7 and fe80::/10 before TLS starts. Rejections are reported to the UI.
**Consequences.** Port-forwarded internet traffic is refused even if a router exposes the port. Disabling the filter will need an explicit, warned setting (Phase 5/8).

## ADR-012 — Phase 1 password: random, shown in the menu
**Context.** Onboarding (Phase 5) is where the user chooses the password; Phase 1 needs something secure now.
**Decision.** Generate a 20-character password (unambiguous alphabet, about 115 bits) with `SecRandomCopyBytes` and rejection sampling, store it in the Keychain, and expose it through **Copy Password** in the menu. The username is the macOS short name.
**Consequences.** Phase 5 replaces generation with user choice and adds a strength check.

## ADR-013 — Ad-hoc dev builds store secrets in an owner-only file, not the Keychain
**Context.** The login keychain records which app may read an item using that app's code signature. For ad-hoc signatures it pins the exact build hash, and an explicit designated requirement (tried and verified 2026-10-21) does not change that. So every rebuild triggers a password prompt for the login keychain, which blocks development and won't work for users who don't know that password. The Data Protection keychain needs an application-identifier entitlement, which ad-hoc builds can't have.
**Decision.** `SecretStores.default()` checks the running signature. With a team identifier (Developer ID / Apple Development) it uses `KeychainStore`. Otherwise it uses `FileSecretStore` at `~/Library/Application Support/ClawTank/secrets/` (directory 0700, files 0600, excluded from backups). Files are created 0600 *before* the secret is written.
**Consequences.** In unsigned builds, any process running as the same user can read the TLS key and RDP password. That's similar to the exposure an ad-hoc Keychain item would give, and it's documented for users of unsigned builds. Signed releases keep Keychain protection. A future "migrate secrets" step is needed if a user switches from an unsigned to a signed build (Phase 10).

## ADR-014 — EGFX AVC420 only in Phase 2; legacy clients see the test pattern
**Context.** Every target client (mstsc, Windows App, FreeRDP) supports the Graphics Pipeline with AVC420. A bitmap or RemoteFX fallback for clients without EGFX would mean a second, CPU-heavy video path.
**Decision.** Live video goes only over EGFX AVC420. A client that doesn't open the graphics channel keeps the static test frame from the legacy display handler. The H.264 bitstream is Annex-B, per MS-RDPEGFX RFX_AVC420_BITMAP_STREAM (IronRDP's client docs say "AVC length-prefixed", which conflicts with the spec). Coded size is 16-aligned, with ScreenCaptureKit placing content top-left via `destinationRect`, and the region rect crops to the desktop size.
**Consequences.** We revisit a fallback if a real client needs one.

## ADR-015 — Dev builds signed with a local self-signed identity
**Context.** TCC (Screen Recording, Accessibility) and the Keychain pin ad-hoc-signed apps to their build hash, so every rebuild loses permission grants. The maintainer can't unlock the login keychain.
**Decision.** `scripts/dev-signing.sh` creates `~/Library/Keychains/clawtank-dev.keychain-db`. It has its own random password (git-ignored `build/dev-signing/`) and holds a self-signed "ClawTank Dev" code-signing identity. `make app` re-signs with it when present. The designated requirement becomes `identifier "dev.clawtank.ClawTank" and certificate leaf = H"…"`, which is stable across rebuilds. codesign only finds keys in search-list keychains, so the script adds the dev keychain for the duration of signing and then restores the exact previous list.
**Consequences.** Grants survive rebuilds on this machine. Other machines or CI stay ad-hoc. `scripts/dev-signing.sh remove` undoes it. The identity has no team ID, so secrets still use the file store (ADR-013).

## ADR-016 — VideoToolbox low-latency rate control by default
**Context.** Measured with `make bench` (2560×1600, synthetic motion, paced at 60 fps, M2): standard hardware encoder `ave.avc` gave 59.7 fps, p50 11.6 ms, p95 37.5 ms. Low-latency rate control `h264.rtvc` gave 57.8 fps, p50 11.0 ms, p95 20.3 ms. The rtvc encoder doesn't answer `UsingHardwareAcceleratedVideoEncoder` (-12900) but is created under `RequireHardwareAcceleratedVideoEncoder`.
**Decision.** Use `EnableLowLatencyRateControl` with hardware required. Keep the setting switchable (`Settings.lowLatencyRateControl`) and log the encoder ID.
**Consequences.** Re-benchmark on real desktop content and judge text quality visually in a client. If rtvc's quality or rate control is worse for text, quality presets (Phase 5) may pick `ave.avc`.

## ADR-017 — Temporary vendored `ironrdp-server` 0.13.0 with two upstream fixes
**Context.** The published 0.13.0 maps the middle button and horizontal wheel to *moves*, and maps the X1/X2 (back/forward) buttons to **left/right clicks**. It also sends 32 bpp pointers with an empty AND mask, which Windows App for macOS ignores (it keeps its default arrow). IronRDP master fixes both, but they aren't released.
**Decision.** Vendor 0.13.0 under `core/vendor/ironrdp-server` via `[patch.crates-io]`, changing only (1) the `MousePdu`/`MouseXPdu` conversions in `handler.rs` (plus a `HorizontalScroll` variant) and (2) the AND mask derived from alpha (`encoder/pointer_mask.rs`, copied from master). Both are marked `ClawTank patch`. The vendor directory is excluded from our workspace lints. Chosen by the maintainer over moving to IronRDP master.
**Consequences.** Remove it when IronRDP publishes a release with these fixes; `diff -r` against the registry copy shows the full delta. Licensing is Apache-2.0 OR MIT, credited in THIRD_PARTY_NOTICES.

## ADR-018 — Locked screen: detect and tell; remote unlock is research
**Context.** Found live in Phase 5. When the Mac is locked, ScreenCaptureKit returns only the wallpaper (the lock-screen UI and all windows are excluded), and macOS doesn't accept synthetic keystrokes into the lock screen, so a remote user can't unlock it. A headless Mac mini that locks after sleep would then be unusable remotely.
**Decision (now).** Keep the Mac awake during sessions (`PowerAssertions`, default on) so it doesn't lock mid-session. Track `com.apple.screenIsLocked`/`screenIsUnlocked` and show the state in the menu and log. Document the recommended headless setup in the user guide: automatic login, plus "require password after screen saver" set to a long delay or off on a trusted network.
**Research (Phase 8/10).** Options to unlock remotely without weakening security, all needing investigation: whether a privileged helper can post input to `loginwindow`; how Apple's Screen Sharing unlock flow works through public mechanisms; FileVault considerations. No implementation is promised.
**Consequences.** Until then, a locked Mac shows wallpaper to remote clients, and the menu says why.

## ADR-019 — Multi-monitor deferred
**Context.** ironrdp-server 0.13 / ironrdp-acceptor 0.10 ignore the client's GCC monitor data, always send a single-monitor Monitor Layout PDU, and cap Display Control at 1 monitor. IronRDP master only *records* client monitors, and its acceptor still describes one monitor. Supporting it would mean patching two more upstream crates, including connection-sequence code, plus per-monitor virtual displays, capture and encoders.
**Decision.** Chosen by the maintainer: defer. Multi-monitor clients get one resizable desktop. Revisit when IronRDP gains server multi-monitor support, or contribute it upstream.
**Consequences.** The Phase 7 "two-monitor session" acceptance item is not met in v1.

## ADR-020 — Adaptive bitrate from EGFX acknowledgements
**Context.** Wi-Fi throughput and latency vary; a fixed bit rate either wastes quality on good links or stalls bad ones.
**Decision.** The core times each frame from send to client ack (EWMA, α = 1/8) and reports frames in flight and backpressure skips. Once a second the host's `AdaptiveBitrate` runs:
- Back off ×0.7 on congestion: more than 2 skips, more than 6 frames in flight, or ack latency above max(80 ms, 3× the best seen).
- Recover ×1.15 after 3 healthy seconds.
- Stay between target/6 and the preset's target.

Changes apply live with `VTSessionSetProperty`, with no keyframe.
**Consequences.** Needs tuning on real Wi-Fi (human checklist). The menu shows rtt, target rate and a congestion flag.
